Deployed. Still the old version?دیپلوی شد. هنوز نسخهٔ قدیمی؟

The fix is live, but you still see the old page. whycached sends a few harmless GET requests to the URL you are looking at, compares what comes back, and says which layer is serving the stale copy: a CDN, your browser, a service worker, or an asset that never changes name. It prints the evidence and the fix for that layer, and it never purges anything.اصلاح بالاست ولی هنوز صفحهٔ قدیمی را می‌بینید. whycached چند درخواست GET بی‌خطر به نشانی‌ای که نگاه می‌کنید می‌فرستد، پاسخ‌ها را مقایسه می‌کند و می‌گوید کدام لایه نسخهٔ کهنه را می‌دهد: CDN، مرورگر شما، service worker یا فایلی که نامش هیچ‌وقت عوض نمی‌شود. شاهد و راه‌حل همان لایه را چاپ می‌کند و هیچ‌چیز را purge نمی‌کند.

    The problemمسئله

    Deployed, but you still see the old version? whycached finds which cache layer is serving it.دیپلوی کردید ولی هنوز نسخهٔ قدیمی را می‌بینید؟ whycached پیدا می‌کند کدام لایهٔ کش آن را می‌دهد.

    The problemمسئله

    You deployed, the fix is live, and the page still shows the old version. Is it the CDN, your browser, a service worker, a one-year max-age on app.js, or did the deploy not finish? People purge everything, hard-reload for an hour, or ask an AI agent that cannot see the headers, and the same correct code is "fixed" again.دیپلوی کردید، اصلاح بالاست و صفحه هنوز نسخهٔ قدیمی را نشان می‌دهد. کار CDN است، مرورگر، service worker، یک سال max-age روی app.js، یا دیپلوی تمام نشده؟ آدم‌ها همه‌چیز را purge می‌کنند، یک ساعت hard reload می‌زنند یا از ایجنتی می‌پرسند که هدرها را نمی‌بیند و همان کد درست دوباره «درست» می‌شود.

    What it doesچه می‌کند

    Point it at the URL you are actually seeing. It sends only GET requests, the same URL four ways (normal twice, cache-busted, with Cache-Control: no-cache, conditional), compares the bytes, and reasons per layer: a shared cache (Cloudflare, Fastly, GitHub Pages, Vercel, CloudFront, Netlify, Akamai and others) that is confirmed stale, how long your browser may legally reuse its copy, a service worker that answers before the network, and assets cached for a year under a name that never changes. Every finding comes with evidence and the fix for that layer. It never purges anything.آن را روی نشانی‌ای که واقعاً می‌بینید بزنید. فقط درخواست GET می‌فرستد، همان نشانی را به چهار شکل (عادی دو بار، با پارامتر شکستن کش، با Cache-Control: no-cache و شرطی)، بایت‌ها را مقایسه می‌کند و برای هر لایه استدلال می‌کند: کش مشترک (Cloudflare، Fastly، GitHub Pages، Vercel، CloudFront، Netlify، Akamai و…) که قطعاً کهنه است، مدتی که مرورگر قانوناً می‌تواند نسخهٔ خود را نگه دارد، service workerی که پیش از شبکه جواب می‌دهد و فایل‌هایی که یک سال با نامی ثابت کش شده‌اند. هر یافته با شاهد و راه‌حل همان لایه می‌آید. هیچ‌چیز را purge نمی‌کند.

    • 4۴request variants compared for every URLنوع درخواست مقایسه‌شده برای هر نشانی
    • 31۳۱tests, local servers only, no internetآزمون، فقط سرور محلی و بدون اینترنت
    • 0۰dependencies · GET requests onlyوابستگی · فقط درخواست GET

    Featuresامکانات

    What it does, precisely.دقیقاً چه می‌کند.

    01

    A CDN serving an older copyCDN که نسخهٔ قدیمی‌تر می‌دهد

    If the normal response differs from the cache-busted or no-cache one, or your --expect string is missing in one and present in the other, it is STALE: the vendor, the Age of the copy, how long it stays fresh and the purge command for that CDN.اگر پاسخ عادی با پاسخ بدون‌کش یا no-cache فرق داشته باشد، یا رشتهٔ --expect شما در یکی نباشد و در دیگری باشد، نتیجه STALE است: نام فروشنده، Age نسخه، مدت تازگی و دستور purge همان CDN.

    02

    What your browser may legally keepآنچه مرورگر قانوناً می‌تواند نگه دارد

    Computes private-cache freshness, including the 10 % heuristic when only Last-Modified is sent, and says for how long a browser may reuse its copy without asking the server, with the hard-reload recipe.تازگی کش خصوصی را حساب می‌کند، از جمله قاعدهٔ ۱۰٪ وقتی فقط Last-Modified فرستاده شده، و می‌گوید مرورگر تا چه مدت بی‌پرسیدن از سرور می‌تواند نسخهٔ خود را بدهد، با روش hard reload.

    03

    A service worker answering firstservice workerی که اول جواب می‌دهد

    Finds serviceWorker.register(...) in the HTML, reads the worker (Cache API, Workbox, cache-first, skipWaiting, cache names) and flags the classic bug: a worker script served with a long max-age.فراخوانی serviceWorker.register(...) را در HTML پیدا می‌کند، worker را می‌خواند (Cache API، Workbox، cache-first، skipWaiting، نام کش‌ها) و باگ کلاسیک را نشان می‌دهد: فایل worker با max-age طولانی.

    04

    Assets that never change nameفایل‌هایی که نامشان هیچ‌وقت عوض نمی‌شود

    Linked same-origin CSS and JS cached for a day or more under a name with no hash or version: the reason users keep an old app.js after a deploy.فایل‌های CSS و JS هم‌مبدأ که یک روز یا بیشتر با نامی بدون هش یا نسخه کش شده‌اند: دلیل اینکه کاربران پس از دیپلوی app.js قدیمی را نگه می‌دارند.

    05

    Not a cache problem, and it says soمشکل کش نیست، و می‌گوید نیست

    If your --expect string is in no response at all, the cause is not caching: the deploy has not finished, or you are looking at the wrong environment. It stops you from purging a CDN that is innocent.اگر رشتهٔ --expect در هیچ پاسخی نباشد، علت کش نیست: دیپلوی تمام نشده یا محیط اشتباه است. جلوی purge کردن CDNی که بی‌گناه است را می‌گیرد.

    06

    Made for humans and agentsبرای آدم‌ها و ایجنت‌ها

    --json for scripts, exit code 1 when something is STALE or LIKELY, and a snippet for AGENTS.md / CLAUDE.md so an agent runs it before it edits code that was already correct.خروجی --json برای اسکریپت، کد خروج ۱ وقتی چیزی STALE یا LIKELY باشد و یک snippet برای AGENTS.md / CLAUDE.md تا ایجنت پیش از ویرایش کدِ از قبل درست آن را اجرا کند.

    How it worksچطور کار می‌کند

    Four steps, no magic.چهار گام، بدون جادو.

    Four requests, same URLچهار درخواست، یک نشانی

    Normal twice (hit/miss transition, Age), with a unique ?_whycached= parameter (close to the origin), with Cache-Control: no-cache, and conditional (If-None-Match / If-Modified-Since). Only GET is ever sent.عادی دو بار (گذار hit/miss، Age)، با پارامتر یکتای ‎?_whycached=‎ (نزدیک به origin)، با Cache-Control: no-cache و شرطی (If-None-Match / If-Modified-Since). فقط GET فرستاده می‌شود.

    Compare the bytesمقایسهٔ بایت‌ها

    If the normal response differs from the cache-busted or no-cache one, or your --expect string is only in the fresh one, a shared cache is confirmed stale. If --expect is in neither, the deploy has not finished.اگر پاسخ عادی با پاسخ بدون‌کش یا no-cache فرق کند یا رشتهٔ --expect فقط در پاسخ تازه باشد، کهنگی کش مشترک تأیید می‌شود. اگر --expect در هیچ‌کدام نباشد دیپلوی تمام نشده است.

    Reason per layerاستدلال برای هر لایه

    Vendor signatures (CF-Cache-Status, x-vercel-cache, X-Cache, Cache-Status and more), private-cache freshness for the browser, the service worker script, and linked CSS/JS names and max-age.امضای فروشنده‌ها (‏CF-Cache-Status، ‏x-vercel-cache، ‏X-Cache، ‏Cache-Status و…)، تازگی کش خصوصی برای مرورگر، فایل service worker و نام و max-age فایل‌های CSS/JS لینک‌شده.

    Four levels, one fix eachچهار سطح، هرکدام یک راه‌حل

    STALE (confirmed), LIKELY (a legitimate reason your browser can show the old copy), NOTE, OK. Each has the vendor-specific purge or the header to send; exit code 1 for STALE or LIKELY, 2 when it could not fetch.STALE (تأییدشده)، LIKELY (دلیل موجهی که مرورگر نسخهٔ قدیمی را نشان دهد)، NOTE و OK. هرکدام دستور purge مخصوص فروشنده یا هدر لازم را دارد؛ کد خروج ۱ برای STALE یا LIKELY و ۲ وقتی دریافت ممکن نشد.

    Honest limitsمحدودیت‌های صادقانه

    What it does not do. Please read.چه کارهایی نمی‌کند. لطفاً بخوانید.

    • It cannot see inside your browser. Browser and service-worker findings are reasons it can happen, never proof that your tab is stale; a hard reload or a private window settles it.درون مرورگر شما را نمی‌بیند. یافته‌های مرورگر و service worker دلیل‌های «ممکن است» هستند، نه اثبات کهنگی تب شما؛ hard reload یا پنجرهٔ خصوصی تکلیف را روشن می‌کند.
    • The cache-busted request is not guaranteed to reach the origin: some CDNs ignore the query string in the cache key and a difference can be hidden. The no-cache probe and --expect are independent cross-checks.درخواست با پارامتر شکستن کش تضمینی ندارد که به origin برسد: بعضی CDNها query string را در کلید کش نادیده می‌گیرند و اختلاف می‌تواند پنهان بماند. پروب no-cache و --expect بررسی‌های مستقل‌اند.
    • Per-user, per-region and per-device caches (CDN points of presence, Vary, cookies) may differ from what this machine sees. Login-protected pages need -H.کش‌های مخصوص کاربر، منطقه و دستگاه (نقاط حضور CDN، ‏Vary، کوکی) ممکن است با آنچه این دستگاه می‌بیند فرق کنند. صفحات پشت ورود به -H نیاز دارند.
    • Header signatures reflect public vendor behaviour as of October 2026 and may drift. Tested on Linux only; macOS and Windows should work (standard library) but are untested.امضای هدرها رفتار عمومی فروشنده‌ها تا اکتبر ۲۰۲۶ را نشان می‌دهد و ممکن است تغییر کند. فقط روی لینوکس آزموده شده؛ macOS و ویندوز باید کار کنند (کتابخانهٔ استاندارد) ولی آزموده نشده‌اند.

    FAQپرسش‌های متداول

    Questions people ask.پرسش‌هایی که می‌پرسند.

    Does it purge or change anything?آیا چیزی را purge یا تغییر می‌دهد؟

    No. It sends only GET requests and prints the purge command; you decide whether to run it.نه. فقط درخواست GET می‌فرستد و دستور purge را چاپ می‌کند؛ اجرایش با شماست.

    What is --expect for?‎--expect برای چیست؟

    Give it a string that should be in the NEW version (a version number, a commit hash, a changed sentence). Then a missing string in the normal response but present in the fresh one is proof, not a hint. If it is in neither, the cause is not caching at all.رشته‌ای بدهید که باید در نسخهٔ جدید باشد (شمارهٔ نسخه، هش کامیت، جمله‌ای که عوض شده). آن‌وقت نبودنش در پاسخ عادی و بودنش در پاسخ تازه اثبات است، نه حدس. اگر در هیچ‌کدام نبود علت اصلاً کش نیست.

    Can it tell me my own browser is stale?آیا می‌تواند بگوید مرورگر خودم کهنه است؟

    No, it runs outside the browser. It tells you for how long a browser may legitimately reuse its copy, which is the LIKELY level. A hard reload or a private window settles it.نه، بیرون از مرورگر اجرا می‌شود. می‌گوید مرورگر تا چه مدت قانوناً می‌تواند نسخهٔ خود را بدهد، یعنی سطح LIKELY. hard reload یا پنجرهٔ خصوصی تکلیف را روشن می‌کند.
